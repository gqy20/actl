## 方法：为什么是"注入轨"

机器注入（actl CLI / computer use 的 SendInput）在低级钩子里带 INJECTED 标志——**录制按设计只编译人工演示**，所以自驱轮覆盖：钩子真实安装、事件捕获、点击反查、焦点身份、值读回、注入标记与编译排除、会话协议。**编译出非空草稿需要人手**（人工演示轨，本验收后建议的下一轮）。为使注入轨有意义，先落地了"注入事件全量捕获（反查/焦点/值读回）但编译侧排除"（提交 c183812——分离进程只读查询无发现 #4 的同进程并发问题，且 trace 记录机器动作带目标身份，诊断价值更高）。

## 四轮经过与发现

**第一轮（rec-ma-1，binary 84079167）**——记录了三个真实缺陷：

1. **DPI 坐标口径错位**：物理点击反查命中**隔壁屏（用户 ChatGPT）的"科研"元素**、窗口元数据全空（hwnd:0）——钩子坐标是物理屏幕坐标，而 `WindowFromPoint`/`ElementFromPoint` 按调用线程 DPI 感知解释，混合 DPI 双屏下错位。
2. **键盘注入位误用**：`KBDLLHOOKSTRUCT` 的 INJECTED 是 **0x10（LLKHF_INJECTED）**，首版用了 0x1（那是 EXTENDED 位；鼠标侧 LLMHF_INJECTED=0x1 恰好同位掩盖了差异）——enter 与 VK_PACKET 键全部漏标，机器输入伪装成人工输入进入编译路径。
3. **值读回静默缺失**：Win11 记事本 Document 的 ValuePattern 读取路径无产出（需 Value→Text 回退链）。

**第二轮（rec-ma-2，binary 5c53e0c5）**——三修复全部真机验证：点击反查命中记事本 Document（窗口元数据完整、dpi=192 证实假设）；23 个键事件全部 `injected:true`（零漏标）；值读回事件出现（两处，含 enter 后形态）。

**第三轮（rec-ma-3，受控对照）**——发现 #4 并证实保真度：

4. **值读回竞态**：type 后立即 record-stop（停止距最后按键 231ms），文档尚未提交→读到空→值事件缺失。修复：读回有界沉降重试（≤3 次 × 150ms，提交 7aa2c26）。
5. **保真度证实**：注入 13 字符 `UNIQROUND3qzx` → 会话恢复后 `verify --value` 精确匹配（`actual == expected`，value-pattern 通道）——注入→文档→读回链路无损。

**第四轮（rec-ma-4，binary bf6758d1）**——**被环境阻断**：用户锁屏离开（前台=Windows 默认锁屏界面，Input Occlusion Window 盖住第二显示器），点击被遮挡守卫正确拒绝、显示端如实报 not ready。**沉降修复的真机复验挂起**（等桌面可用），非代码回归——护栏行为符合设计。

## 观察：第二轮的并发用户输入

第二轮的值读回显示文档含 `hello gggggggg…` 内容（非注入的两段文本），而 trace 内**零个非注入键事件**、逐事件全部对账（1 点击+22 键+1 enter+2 值）。结合第三轮的保真度对照，判定：g 内容为**录制窗口之外**（探测/脚本准备的分钟级间隙）进入文档的用户真实输入。遗留问题（如实）："用户在录制窗口内的输入是否必然被钩子捕获"未在本轮直接验证——留给人工演示轨（用户在录制中故意输入即可顺带裁定）。

## 结论

注入轨真机验收通过：捕获管线在真实桌面、真实混合 DPI、真实并发用户环境下工作，四个发现全部定位到根因并修复（#1 DPI 线程感知、#2 LLKHF 位、#3 Value→Text 回退、#4 沉降重试——前三者真机复验通过）。人工演示轨是下一轮（用户在场 2 分钟即可：record-start → 手动打字/点击 → record-stop → 检查草稿），它同时裁定"录制窗口内用户输入必被捕获"的遗留问题。

## 人工演示轨（2026-10-04 增补）：右键链路 + 真人输入 + IME——通过

用户在场的真实演示轮（会话 `rec-1791083619249`，右键菜单启动/停止——R4 链路随行验收）：

**演示内容**（uTools 唤起记事本 → 输入中英文 → ctrl+s → 关闭标签）：47 事件（**43 个非注入真人输入**）、`skipped_own: 5`（右键菜单的两次开合+点击被 actl-signal pid 过滤正确排除——"点录制 UI 自己"不进 trace 的设计实证）、**10 步 + 6 TODO 的首份真人草稿**。

**逐项断言**：

- **R4 右键链路 ✓**：菜单「开始录制」spawn 会话（auto-id）、「停止录制」等终态返回摘要（"录制已完成：47 事件 → 10 步 + 6 TODO"进信号条 details 反馈）；
- **真人输入捕获 ✓**：43/47 非注入事件全部入 trace 并编译——上一轮遗留问题"录制窗口内用户输入必被捕获"就此裁定（肯定答案）；
- **IME 中文值读回 ✓（旗舰断言）**：用户经输入法打出的「测试一下小过 」被 burst 末值读回捕获，编译为 `type "测试一下小过 " --paste`（提交文本覆盖 VK 推导——该 IME 不产生 VK_PROCESSKEY，若信 VK 会编译出拼音乱码；提交值优先的设计在真实输入法上恰好成立）；
- **wait 步骤 ✓**：uTools→记事本 7 秒换窗间隔编译出 `wait --window marker4.txt - Notepad --timeout 8022`（真实时延分析）；
- **{window} 泛化 ✓**：三个窗口（uTools/marker4/marker3）收编为三个 inputs。

**发现 #5（演示轮抓出，离线测试全漏）**：`--timeout 8022` 裸数字渲染——YAML 解析为整数，flow schema 要求 args 全字符串 → 草稿 flow-validate 拒绝。根因：`yaml_scalar` 不引数字/布尔/null 形态纯量（route 渲染同源缺陷，既往数据无数字参数故未暴露）。修复：数字/布尔/null 形态强制加引号（提交随本增补）；补单测 + roundtrip 断言（wait 超时参数必须字符串）。

**R3 首次真实改写 ✓**：按 record-rewrite.md 程序对该会话做最小机械改写（数字参数加引号）→ `rewritten.yml` → flow-validate 通过（10 步）。此草稿由修复前二进制产出（含裸数字，验证失败属预期）；修复后二进制的草稿不再有此缺陷（单测钉住）。

**如实边界**：发现 #4（读回竞态的沉降重试路径）本轮仍未被触发（用户停录前最后动作是点击，非紧贴键入的即时停止）——复验仍挂；6 个 TODO 形态符合设计（uTools 唤起热键 vk 0xC0 布局相关键名、enter 终结键、4 个退格编辑手势）；草稿含 s6/s7 重复 ctrl+s（用户按了两次——机械如实记录，噪音清除属改写轮）。

## 改写重放轮（2026-10-04 增补）：R3 完整改写 → 真机重放六轮 → 通过

对演示会话 `rec-1791083619249` 的 `rewritten.yml` 做完整 agent 改写（v1→v6），六轮真机重放（demo-rewrite-005…010，run 级证据存 target/acceptance-record/）。**010 全链通过（11 步 completed）**：uTools 逐键搜索 → enter 启动记事本 → ctrl+O 打开 marker4 → 全选替换输入「测试一下小过 」→ 保存 → 关标签 → 关窗；marker4.txt 落盘内容逐字节等于输入（含尾随空格），现场归零（记事本 absent 核验）。

**发现 #7（识图对比实证）**：uTools 搜索框不吃粘贴——ctrl+v 只生成关键词标签、不驱动模糊筛选（结果列表保持默认全集，回车命中默认首项「文件搜索」而非记事本）；真实击键逐键 press 与手敲同通道（识图实证 jishi 后记事本橙色高亮居首）。v2 剪贴板通道因此整体废弃；搜索词无法参数化（每字母一步）是该通道的固有代价。

**发现 #8**：演示里「enter 后窗口标题=marker4.txt - Notepad」是标签会话巧合——重放时会话恢复的活动标签是 marker/marker3（无 marker4）。修正：enter 步只断言「记事本出现」，新增 ctrl+O 文件对话框三步显式打开工作文件，流程对任意标签会话状态幂等。

**发现 #9（用户指出：输入前没有清除已有内容）**：preflight backspace×2 按数清不净残留（005 轮 jishi+残留=jisjishi 无命中）。修正：全选删除对任意残留幂等，v6 并入流程首部 sequence 步。

**发现 #10**：原生文件对话框文件名控件是同名父子（ComboBox「文件名(N):」内嵌 Edit「文件名(N):」）——name 子串匹配双双命中 AMBIGUOUS。修正：严格匹配 `uia:{"match":{"role":"Edit","name":"文件名(N):"}}` 定位 Edit。

**引擎语义澄清（误诊教训）**：`flow-resume` 不带 `--retry-step` 对 uncertain 步是 no-op（engine 只重发布状态并提示授权 retry）——007 两轮 resume 的「字母没落地」实为步骤根本没执行，一度误诊为清空序列打飞了输入焦点（focus-report 证伪：焦点一直在输入框）。另：键名是 `esc` 不是 `escape`（PROTOCOL 拒绝，两轮 esc 隐藏计划因此从未生效）。

**验收脚本纪律再犯（用户指出）**：005-009 的一站式驱动脚本（driver*.ps1/sh）违反「YAML 流程优先于一次性脚本」（AGENTS 验收纪律 #1，2026-10-02 已沉淀过同一教训）——前置清空/marker4 预清空本可治理为流程步骤或幂等设计。v6 收敛：清空并入幂等 sequence 步、记事本输入改 ctrl+a 全选 + type --paste 替换（消灭 marker4 预清空前置）、s1 只读前置检查；流程外前置只剩「uTools 已唤起」（actl 无应用启动命令）。

**键入速度实测**：009（13 步逐键）24.1s vs 010（11 步、两个 sequence 组）34.4s——sequence 摊薄的是步级预告，**每次按键 ~1s 的前台/焦点安全守卫成本逐键照付**（fail-closed 输入护栏，设计使然；modifier_wait 对无修饰键有快速路径，非热点）。树不可见目标无法走 type 通道（locate 无焦点元素目标语法）→ 真正的 burst 打字（守卫一次、注入一词）是 spec 级特性，入 ROADMAP 候选，不在改写轮静默实现。

**如实边界**：发现 #4 沉降路径仍未被触发（复验挂起不变）；010 的 s1 只读步无 verify 属性（只读步免验证，schema 允许）；演示会话遗留的 marker3/marker 脏标签经两轮优雅关闭丢弃未保存缓冲（夹具文件本体未动）；005-009 失败 run 的状态按纪律保留（needs_review，不改写历史计划）。
