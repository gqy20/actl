# YAML 流程 v1 测试与体验评估

日期：2026-09-27。实现提交：38bf625；本轮另补断言预检修正及可复现评估脚本。

## 结论

可以用于步骤明确、有稳定语义选择器和结果断言的顺序任务。暂停、恢复和异常退出已有可验证的
执行语义，适合作为第一版流程基础。复杂任务的结果传递、人工介入说明和快速暂停仍需要补齐。
本结论不等同于真实业务应用的生产验收。

## 发现并修正的问题

`flow-validate` 原先通过 clap 校验后，未继续检查 wait/verify 的运行时断言要求。
无条件 wait 可以预检成功，运行到该步才失败；若前面有写操作，会增加恢复成本。

先新增复现测试确认失败，再补齐：wait/verify 恰好一个断言模式、断言选择器语法和 wait 属性谓词。
同一校验覆盖 run/before/verify；非法流程在建立运行目录前拒绝。预检不检查当前窗口实际存在，
也不能判断用户编写的后置断言是否足以证明业务成功。

## 体验评估

### 已达到的效果

- 暂停请求和暂停确认分开，下一步不会越过暂停边界。
- 恢复能跳过完成步骤，不依赖原 YAML 仍在原位置或保持原内容。
- 错误、停止、中断、需核对结果有不同机器状态，智能体可以据此选择下一步。
- 新运行 ID 与操作历史关联，能追溯执行次数与动作阶段。

### 仍有明显改善空间

1. **长调用期间暂停不够快**：wait 自身还不会读取流程暂停请求，只在返回后暂停。
   当前实现诚实显示等待确认，但不能承诺即时接管。优先让可协作的 wait 轮询响应暂停；
   不应强杀 COM 调用来缩短表面耗时。
2. **暂停原因不够直观**：运行记录有 reason 和步骤错误码，显示信号仅传递流程标题与状态。
   用户界面需要区分计划检查点、用户请求和执行失败，并给出一条下一步建议。
3. **步骤结果不能传递**：adapter 丢弃命令 data，只有成功/失败进入执行判断。
   查询后按查询结果决定目标的复杂任务仍需智能体在外部观察；后续优先做按需结果查看和受限输出绑定。
4. **计划修改成本较高**：原计划固定提高了恢复可靠性，但修改后必须新建运行。
   后续应引入计划修订和已完成步骤兼容性检查，不能简单沿用旧完成标记。

托盘入口与视觉状态本轮只经过编译和现有模型/绘制测试；没有重启用户当前显示端进行点击验收。
跨 DPI、屏幕阅读器以及真实写入应用的完整体验需要另做真机回归。
