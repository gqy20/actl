# 02 · 差距分析:现有方案距离"Quicker 级 AI-native CLI"有多远

日期:2026-09-26

## 1. 总评

**目标被三个项目各拿走三分之一:agent-desktop 拿走"协议",terminator 拿走"Windows UIA 落地",AutoHotkey 拿走"能力覆盖"——三者的交集是空集。**

## 2. 差距矩阵

| 维度 | 目标 | agent-desktop | terminator | AutoHotkey |
|---|---|---|---|---|
| 操作原语覆盖(键鼠/窗口/剪贴板/应用/系统) | Quicker 全覆盖 | 中(54 命令,系统级薄) | 中(命令面不透明) | **满分**(20 年积累,超 Quicker) |
| 感知:语义树而非像素 | 必须 | **优**(ref + skeleton 投影) | 良(UIA 选择器) | 差(HWND 级,UIA 弱) |
| AI-native 输出(envelope/错误码/重试语义) | 必须 | **优**(版本化契约) | 未验证(CLI 是附属品) | 无 |
| Windows 完整可用 | 必须 | **零**(Planned,crate 仅 76 行) | **有** | **有** |
| 工程成熟度 | 高 | 低 | 中(2900+ commits) | **高** |
| 对我们的现实可用度 | — | ≈0(平台不符) | ~50% | ~20%(反馈回路差) |

## 3. 关键缺口(按要害排序)

1. **Windows 上没有 agent-desktop 级的输出协议**——JSON envelope、稳定 ref(`@e3` + STALE_REF 重试语义)、机器可读错误码、token 投影。这是唯一的硬缺口:AHK 有能力没协议,terminator 有平台没协议重心。
2. **命令面深度**——系统级操作(剪贴板历史、通知、托盘、多显示器、文件对话框、UAC 行为)两个新项目都没碰;这块知识只存在于 AHK 社区 20 年的积累里。
3. **UIA 的现实坑**——Chromium/Electron 应用 UIA 暴露质量参差、跨完整性级别受 UIPI 限制、老 Win32 应用只有 HWND。Quicker 用户踩平了,新项目都还没经历。
4. **反馈回路粒度**——AHK 模式(AI 写整段脚本→执行)是"批发";需要的是原子命令"零售",每步拿结构化结果再决定下一步。这是可靠性差距,不是功能差距。

## 4. 一个"不是缺口的缺口"

Quicker 的**动作编辑器、触发面板、动作市场**三层,在本架构中不需要 CLI 承担:

- 编排层:agent 的工具循环免费获得(自然语言取代可视化编辑器);
- 沉淀层:agent 的 skills/memory 承担(取代动作市场);
- 触发层:由 agent 侧入口(如 OpenClaw、定时任务、热键 daemon)承担。

**CLI 只需把原子层做对。** 因此产品范围不是"复刻 Quicker",而是只做其"动作引擎"约 1/4,其余 3/4 被 agent 时代替代——这是形态优势,显著缩小了工程范围。

## 5. 机会判断

- 差距**不是方向未验证**(agent-desktop 的 1.7k★ 验证了需求与协议设计);
- **不是能力不存在**(AHK 证明 Windows 全覆盖可行);
- 而是**没人把"协议"和"平台落地"在 Windows 上焊在一起**。

结论:这是一个**定义清晰、范围收敛的工程空位,不是研究问题**。Windows 位置空着,协议蓝本是 Apache-2.0 可直接沿用。
