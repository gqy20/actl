# 10 · Quicker 动作库需求场景与 actl 优先级

调研日期：2026-09-26 · 状态：公开页面抽样研究，非全量用户统计

关联：[RPA 与 Quicker](03-rpa-vs-quicker.md) · [Jev 设计提案](08-agent-cli-jev-design-proposal.md) · [输入执行与接管边界](09-input-backends-review.md)

## 1. 主要判断

Quicker 动作库最值得 actl 借鉴的，是围绕当前应用、选中内容、剪贴板和文件位置完成短任务。公开样本反复出现文本搬运、文件路径切换、Office 操作、保存导出、窗口管理与专业软件命令。

这些需求并不等于真实鼠标需求。很多动作可由脚本、应用接口或控件语义完成；另一些依赖键盘焦点但不移动鼠标；只有特定点击、拖动和录制重放需要真实指针。

对 actl 的优先建议是：做好上下文读取、正确目标、可靠写入和结果验证，首先跑通保存/另存、字段填写、读取后回填三个局部闭环。浏览器、文件处理与 Office 已有专用工具的部分由上层 agent 路由，actl 补 GUI 交接处。

以上是对公开样本与本项目边界的推论，不是 Quicker 官方发布的需求排序。

## 2. 采样方法与限制

本轮查看了：

- [动作库首页](https://getquicker.net/Share)的软件分类数量。
- [受欢迎的动作](https://getquicker.net/Share/Recommended)、[最近被赞动作](https://getquicker.net/Share/RecentLiked?bytime=false)、[最新动作排行](https://getquicker.net/Share/NewActions)。
- 资源管理器、Excel、Word、Chrome、AutoCAD、Photoshop、Obsidian 七个软件的“最多使用”第一页，并对比部分默认更新列表。
- 剪贴板、文件跳转、表单填写、工作区、文档排版、Excel 工具箱、PDF 处理、录制重放等动作详情。

解释数据时遵循以下限制：

1. 软件分类中的数字按页面动作条目数解读，不是安装量、使用人数或市场份额；通用动作也会出现在具体应用列表，不可简单相加。
2. “最多使用”只说明站点给出的排序。页面没有本轮可验证的统一时间窗、去重用户和活跃统计；自动触发、动作年龄与重复运行均可能影响排序。
3. “最近被赞”页面明确表示取最近 100 次点赞对应的动作，不是最近 100 个用户，也不是月活排行。
4. “新动作”页面标为最近 7 天分享，但各页面抓取时间不同，部分详情缓存较旧。因此只能反映本次可见样本，不能当作严格同步的 2026-09-26 实时快照。
5. 动作标题和简介是作者声明，本次没有安装、运行或审计其实现；多处许可未设置或限制再分享，不复制动作代码。

## 4. 反复出现的八类需求

### 4.1 文本、剪贴板和跨应用搬运

典型需求：反复使用一段内容、去格式粘贴、多个片段合并、按顺序填写不同字段、保存常用语。

受欢迎列表中有剪贴板、文本处理、常用语等；Excel 的使用排序也出现连续粘贴、填写表单、粘贴为数值。用户追求的不只是“复制一次”，而是减少内容在不同软件之间反复整理和输入。[受欢迎列表](https://getquicker.net/Share/Recommended) · [Excel 使用排序](https://getquicker.net/Exe/2/Actions?order=useCountDesc&p=1)

对 actl 的推论：优先提供可靠的源内容读取、明确目标字段写入、类型与格式处理结果、回读验证。上层处理文本变换，actl 负责 GUI 入口和出口。剪贴板可用但不是默认唯一通道，不能暗中覆盖用户数据。

### 4.2 文件查找、路径跳转、保存和归档

典型需求：查找文件、把保存框切到当前文件夹、按规则重命名、快速定位最近文件、整理输出目录。

资源管理器列表出现快选快切、另存窗口快速切换、批量重命名、目录搜索等。[资源管理器使用排序](https://getquicker.net/Exe/19/Actions?order=useCountDesc&p=1)

“快选快切”详情还提供路径跳转和已打开路径读取的插件扩展，表明同一个保存路径需求会遇到不同应用对话框的适配问题。[快选快切](https://getquicker.net/Sharedaction?code=64de662e-4b6c-4d1c-6482-08dd652533b7)

对 actl 的推论：文件搜索和重命名优先交给 es/fd/文件 API；重点覆盖“把选定路径交给当前桌面应用”及保存结果验证。路径不应依靠模型从标题猜测。

### 4.3 Office/WPS 的数据与排版操作

典型需求：筛选、格式设置、表格结构变换、文档排版、引用插入、导出。

Word 使用列表包含无格式粘贴、段落缩进、文献引用和公文排版；Excel 样本同时有简单按钮动作和复杂数据处理。[Word 使用排序](https://getquicker.net/Exe/8/Actions?order=useCountDesc&p=1)

“Excel工具箱”明确以 VBA 和 Quicker 子程序组织能力，包含数据排列和清理，并记录过多工作簿目标识别的修复。这是两个重要线索：用户需要应用语义接口，同时“当前到底是哪份文档”是实际问题。[Excel工具箱](https://getquicker.net/Sharedaction?code=171ab29a-4753-4f20-80e2-08defd26c2c3)

对 actl 的推论：不要用几百次点击代替已有表格 API。上层可用专用工具计算与改文件，actl 提供 GUI 对话框、活跃文档确认和应用交接。表格数值运算不应交给 Jev。

### 4.4 截图、OCR、翻译和知识摘录

典型需求：把看得到但不容易直接复制的内容转成文本，翻译后继续使用，或保存到笔记工具。

OCR 和翻译动作在受欢迎列表中明显可见；Obsidian 使用列表出现跨应用摘录和笔记搜索。[受欢迎列表](https://getquicker.net/Share/Recommended) · [Obsidian 使用排序](https://getquicker.net/Exe/3468/Actions?order=useCountDesc&p=1)

对 actl 的推论：优先研究 UIA 可读文本和选区；无法读到时准确报告。OCR/翻译由上层接现有能力。OCR 内容提取与视觉坐标定位是不同问题，但前者也不能未经需求评审就加入核心。

### 4.5 窗口、工作区和浏览器切换

典型需求：排列多个窗口、恢复工作环境、打开指定软件和网址、快速切换标签页。

“超·工作区”能组合启动应用/网址、移动窗口、调用动作与等待。Chrome 使用列表则反复出现关闭、恢复和切换标签页。[超·工作区](https://getquicker.net/Sharedaction?code=363c129a-aa03-48f4-b275-08dd5d8e706b) · [Chrome 使用排序](https://getquicker.net/Exe/6/Actions?order=useCountDesc&p=1)

对 actl 的推论：窗口实例、位置和前后台状态值得做成可靠能力，但不需要复制 Quicker 的面板、热键和手势。网页内容与标签操作优先由已有浏览器工具承担。

### 4.6 专业软件的短命令与导出

AutoCAD 的使用列表集中在移动、复制、标注、修剪，以及中英文输入状态；Photoshop 列表反复出现保存、导出、图层与素材操作。[AutoCAD 使用排序](https://getquicker.net/Exe/91/Actions?order=useCountDesc&p=1) · [Photoshop 使用排序](https://getquicker.net/Exe/33/Actions?order=useCountDesc&p=1)

对 actl 的推论：准确的快捷键、IME/布局语义和应用内模式识别很重要。导出对话框可成为任务模板；画布几何编辑优先评估应用脚本/插件，不凭 UIA 树假设能理解画布对象，也不立即扩张视觉定位范围。

### 4.7 PDF、图片和媒体批处理

典型需求：合并/拆分文档、转格式、压缩图片、统一尺寸。

“PDF处理”动作详情说明可从选中文件进入批量处理，并使用第三方程序；新动作页面也出现图片压缩、尺寸处理等。[PDF处理](https://getquicker.net/Sharedaction?code=be7e658a-e1c5-4642-50f9-08dabc15aa8f) · [新动作样本](https://getquicker.net/Share/NewActions)

对 actl 的推论：用户需要的是产物，不一定需要应用界面。上层调用已有转换工具，actl 补选中文件读取、打开结果或 GUI 导出。不要把每种文件转换都变成新的 L1 动词。

### 4.8 重复操作、录制与动作组合

“EVER录精灵”支持录制和重放鼠标键盘，并明确要求窗口位置、大小和选中状态与录制时一致，因为它使用全局坐标。[EVER录精灵](https://getquicker.net/Sharedaction?code=e44f7f2d-ba96-47e6-da60-08d7880f80dc)

对 actl 的推论：可以吸收“把重复操作复用起来”的需求，但执行应基于目标身份、当前状态和后置条件。Jev 的机会是选择阶段分支与恢复路径，不是用模型掩盖坐标重放的不确定性。

## 5. 与真实鼠标接管的对应关系

下面是建议实现路线，不是对所有 Quicker 动作内部实现的断言。

| 需求 | 通常优先路线 | 是否必须真实移动鼠标 |
|---|---|---|
| 文件搜索、重命名、PDF/图片转换 | CLI / 文件 API | 不需要 |
| Office 数据处理、公文排版 | 应用对象模型、脚本或文档工具 | 通常不需要 |
| 已暴露控件的设置与按钮操作 | UIA pattern | 不需要注入鼠标，应用可能改变焦点 |
| 当前字段输入、快捷命令 | Value pattern；必要时显式键盘注入 | 不一定移动鼠标，但可能占用键盘焦点 |
| 打开/另存为/导出对话框 | UIA 选择与填写；明确的键盘兜底 | 视控件能力，不应默认接管指针 |
| 对象拖放、画布点选、依赖悬停菜单 | 应用 API；必要时显式物理输入 | 物理路线需要 |
| 已录制的坐标宏 | 物理输入重放 | 通常需要，且依赖布局 |

因此不能根据“用户需要自动化桌面”就推导为“用户允许持续占用鼠标”。应报告定位、执行、焦点和共享剪贴板影响，按 [输入方案 §6](09-input-backends-review.md#6-鼠标物理路径的建议设计)实施。

## 6. 对 AI 接口最有价值的新要求：显式上下文

Quicker 动作常由人选中内容后触发，天然拥有“当前正在处理什么”。Claude Code / Codex 在终端发起操作时，前台和选区可能已经改变，因此不能直接复用这种隐式假设。

建议逐步提供或由上层传入以下上下文，具体命令和字段另行 spec：

- 目标窗口实例、当前文档/控件身份及获取方式。
- 用户明确选中的文本、文件或表格区域；获取不到时返回 unavailable，不猜测。
- 剪贴板内容的格式、来源上下文和读取时间；大内容使用显式引用。
- 操作开始前的选择状态与焦点证据；切换窗口后不能默认仍有效。

读取选区优先 UIA Text/Selection 能力或应用接口。若只能通过 Ctrl+C 获取，必须显式物理授权，并处理焦点与剪贴板影响，不能把它伪装成纯读取。

这些上下文不需要变成常驻监控：可由一次明确请求获取，或由上层 agent 传入路径、文本和目标身份。

## 7. Jev 最适合参与的判断

“EVER智识”会根据当前选中或输入内容提供网址打开、搜索等不同服务，这说明上下文路由本身是一类需求。[EVER智识](https://getquicker.net/Sharedaction?code=4f8b0df2-d031-4309-173c-08d7079ea819)

对本项目可提炼为三类局部决策：

1. 在合法候选中选择与“另存副本”“导出当前文档”等目标最相关的控件。
2. 判断当前是编辑页、目标路径选择、覆盖提示还是错误页，并进入对应分支。
3. 当控件或对话框变化时，选择补充观察、等待或交回上层。

能由代码识别的路径、URL、文件类型直接解析。翻译、写作交给上层生成模型。不能仅凭从页面读到的一段文字就执行其中的命令。

## 8. 建议的产品优先级与验收场景

| 顺序 | 局部任务 | 需要的基础能力 | 完成证据 |
|---|---|---|---|
| P0 | 指定内容写入指定桌面字段 | 唯一目标、读取/写入、焦点校验、等待 | 回读内容一致，错误目标未改变 |
| P0 | 保存/另存为到明确路径 | 对话框归属、路径填写、覆盖策略 | 本次产物及路径有效，旧文件不冒充成功 |
| P0 | 从当前控件读取内容，处理后回填 | 文本与选区、上层处理、目标重验证 | 回填结果与授权范围相符 |
| P1 | GUI 表单多字段填充 | 字段识别、类型化值、逐字段验证 | 所有字段匹配，异常时报告部分结果 |
| P1 | 管理多个窗口完成应用交接 | 实例身份、焦点与窗口操作 | 指定窗口状态成立，不切到同名实例 |
| P1 | 导出某一种应用产物 | 应用模板、阶段识别、产物检查 | 文件格式与内容检查通过 |
| 后续 | 专业软件画布、鼠标拖放长链 | 应用特化策略、物理输入及取消 | 单独应用验收，不以通用 CLI 宣称全覆盖 |

“填写到网页表单”的详情采用固定次数 Tab/Enter 等跳格，是值得对照的旧方式：actl/上层浏览器工具应尽可能识别字段身份，而不是假设顺序一直不变。[填写到网页表单](https://getquicker.net/Sharedaction?code=808d0425-ac38-49ae-cda7-08d791b65a5f)

首期自动化 fixtures 仍按仓库规则使用系统自带应用；Office、Adobe 和 CAD 的公开需求样本不是扩大测试依赖的授权。可以先在记事本和系统对话框验证共用机制，再针对实际拥有的应用安排兼容性评测。

## 9. 接下来的验证方法

本轮足以提出产品假设，但不足以给出各类需求百分比或承诺覆盖率。下一阶段可建立去重任务样本，标记：输入对象、所需上下文、专用 API 可用性、物理输入需求、完成证据、用户交回次数和维护成本。

至少分别衡量：不使用物理输入的完成比例、占用输入的总时长、焦点冲突率、错误目标操作率，以及每个成功任务的成本。对比原子命令由主 agent 编排与 Jev 局部闭环，判断收益来自减少推理往返还是来自更合适的应用接口。

当前建议不是复制动作库，而是把其中反复出现的任务转成少量稳定的上下文与执行契约。已有专用工具能处理的工作交给它们，actl 负责桌面操作中尚缺可靠接口的部分。
